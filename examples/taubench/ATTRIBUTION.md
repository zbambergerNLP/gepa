# Attribution

This directory scaffolds the TauBench evaluation setup for GEPA
(Yao et al. 2024, https://tau-bench.github.io, arXiv:2406.12045),
mirroring the infrastructure of `examples/ifbench/` and `examples/pupa/`.

- Paper & benchmark: **Tau-bench** — Yao, Shunyu et al. "Tau-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains." 2024. Project site https://tau-bench.github.io, code https://github.com/sierra-research/tau-bench. Two domains: **airline** and **retail**, 800+ tasks grounded in tool-augmented user interaction (bookings, order changes, user details, etc.). Each task specifies a user instruction, domain tools, and a success criterion (expected response / database state checked via the simulator's `check_success` / reward).

- Dataset: **HuggingFace `tau-bench/tau-bench`** (800+ tasks). This scaffold loads it via `datasets.load_dataset("tau-bench/tau-bench")` (with a fallback id `tau-bench/Tau-Bench` for registry variants) and flattens all splits. No data files are committed; the loader falls back to `data/taubench.jsonl` if present, else to a synthetic 400-task offline fallback (200 airline + 200 retail) so that `py_compile` and len-check tests pass without network. See `utils.py:load_taubench_dataset` for the full cascade.

- Smoke / fallback: `data/taubench.jsonl` is an optional local JSONL (20–400 lines, one task per line with fields like `task_id`, `domain`, `instruction`/`task`, `expected_answer`, `expected_tool_calls`). The synthetic fallback in `utils.py:_generate_synthetic_tasks` creates deterministic airline/retail instructions with predictable `expected_answer` substrings so the pipeline is exercisable offline.

- Program: Tau-bench's agent must call tools (airline: `get_user_details`, `get_reservation_details`, `search_direct_flight`, `update_reservation`, `cancel_reservation`, …; retail: `get_user_details`, `get_order_details`, `get_product_details`, `modify_pending_order_items`, `cancel_pending_order`, …) over multiple turns. This scaffold implements a **1-stage tool-calling agent** (single `agent_prompt`, one LM call, tools described in the system prompt) and a **2-stage plan-then-act** program (`plan_prompt` → plan, `act_prompt` → act with tools + plan), mirroring IFBench's `generate_response`→`ensure_correct_response` and HotpotQA's `generate_query`→`generate_answer`. Both stages use the same `_call_lm` decoding and thinking-disabled handling. Tool descriptions in `utils.py: AIRLINE_TOOLS_DESC / RETAIL_TOOLS_DESC` are short summaries of the paper's tool specs (see https://github.com/sierra-research/tau-bench/blob/main/tau_bench/envs/airline/tools.py and `retail/tools.py`); the full simulator (stateful DB, tool executor, policy checks) is not bundled for this infra-only scaffold.

- Metric: Tau-bench reports **pass^k / task success** (binary: 1 if the task is resolved correctly, else 0; pass^k aggregates over k stochastic rollouts). `utils.py:taubench_metric` ports this as a single-sample task success (0/1, with 0.5 partial credit for token overlap / partial tool coverage) and per-task feedback (domain, task id, instruction, expected vs observed, reasons), matching IFBench's per-constraint feedback and PUPA's quality+leakage breakdown. When the example carries a `success`/`reward` field (e.g. simulator-checked JSONL), that signal is used directly. A live pass^k should be computed by aggregating k independent rollouts of `taubench_metric` with `k` as the exponent.

- Decoding: `_call_lm` in `utils.py` uses the paper's Qwen3 config from the IFBench artifact (`gepa-ai/gepa-artifact` `experiment_configs.py`: temp=0.6, top_p=0.95, top_k=20, max_tokens=16384, `enable_thinking: False`), shared with `examples/ifbench/utils.py`, `examples/pupa/utils.py`, and `examples/hotpotqa/utils.py` so solver behaviour is identical across benchmarks. Includes truncation and `ContextWindowExceededError` retries.

- Splits: `load_taubench_dataset` follows IFBench/HotpotQA's deterministic seed-0 shuffle and slicing: ≥750 → 150/300/300 (GEPA paper style), ≥320 → 80/80/remainder (~80/80 airline+retail per the task spec), smoke 20 → 14/3/3 (mirrors HotpotQA smoke). `--domain airline|retail` filters before shuffling/splitting. `--train-limit` etc. slice after splitting. See `utils.py` for the full cascade and cycling fallback.

- Code provenance: `utils.py` `_call_lm`, `_strip_think`, `_extract_final_response`, `format_tools` truncation, and `main.py` condition/build_config/action-tracking/diversity/dump helpers are copied from `examples/ifbench/` and `examples/hotpotqa/` to keep all benchmarks consistent. `main.py` supports `--condition vanilla|random|action` (plus `all`/`both` aliases), `--actions default|structured`, `--seed-style plain|structured`, `--max-metric-calls 3500` (spec 3000-5000), `--data-path`, `--train/val/test-limit`, `--domain`, `--program 1stage|2stage`, and `ActionDiversityCallback`, like IFBench/PUPA/HotpotQA.
